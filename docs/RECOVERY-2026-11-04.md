## Развёртывание после восстановления инфраструктуры

1. Восстановить базу и storage, настроить Supabase/SMTP/платёжные ключи вне Git.
2. Проверить историю применённых миграций. Не применять повторно миграции очереди к уже мигрированной базе; при восстановлении старого снимка применять отсутствующие по порядку.
3. Сверить фактические подтверждённые места и очереди с резервной копией перед открытием регистрации. Новый пустой сервер не содержит исторических оплат и не может правильно показать заполненность без восстановления данных.
4. Проверить значения публичного frontend окружения для нового хоста. `npm ci`, `npm test`, `npx tsc --noEmit -p tsconfig.app.json`, `npm run build`.
5. Обновить `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_SSH_KEY` в GitHub Actions. Только после проверки нового сервера установить repository variable `DEPLOY_ENABLED=true`. По умолчанию workflow проверяет/собирает исходники, но не подключается к утраченному серверу.
6. Скрипт `deploy/yookassa-reconcile.py` сначала запускать без `--apply`. Он требует `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_WEBHOOK_URL` и выводит только счётчики. Systemd-файлы — шаблоны, не включаются автоматически. Уведомления и сверку запускать только после восстановления базы.

## Проверки

Сборка Vite, проверка TypeScript, unit-тесты API-верифицированных состояний оплаты и очереди. SQL проверен на отдельном PostgreSQL: лимиты 29/25, подтверждённые места, позиции очереди, неоплаченные анкеты не резервируют места. Проверки фронтенда используют имитацию API: реальный недоступный сервер и реальные оплаты не затрагиваются.
